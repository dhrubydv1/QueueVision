# Sprint 4: Upload API, Live Progress and SQLite — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local FastAPI service where a recorded clip is uploaded, processed in one background thread with live WebSocket progress, stored in SQLite, and replayed on a plain-HTML test page; plus Collective Activity Dataset (CAD) clips, camera configs and a real queue-length accuracy check.

**Architecture:** New `api/` package depends on `ai_engine` (never the reverse). `JobManager` runs `run_tracking.process_video()` in one worker thread, using a new `on_frame` callback to write batched rows to SQLite (stdlib `sqlite3`) and fan messages out to asyncio WebSocket subscribers via `loop.call_soon_threadsafe`.

**Tech Stack:** Python 3.11, FastAPI, uvicorn, python-multipart, sqlite3, httpx (tests), existing OpenCV/Ultralytics engine.

**Spec:** `docs/superpowers/specs/2026-11-04-sprint4-api-design.md` (read it; this plan does not repeat its endpoint table, message fields or table columns).

## Global Constraints

- Branch `sprint-4`; PR into `main`; never push to `main`. The repo is PUBLIC: no uploads, videos, frames, DB files or dataset files in Git (`data/` gitignored; `datasets/raw/` and CAD frames already ignored — check).
- `ai_engine/*` must not import `api`. `ai_engine/queue` and `ai_engine/evaluation` rules unchanged.
- Unit tests run without torch; CI `lint-and-unit` adds only `fastapi`, `uvicorn`, `python-multipart`, `httpx` (pinned) to its install line.
- Pins: `fastapi==0.162.0`, `uvicorn[standard]==0.54.0`, `python-multipart==0.0.33` in `requirements.txt`; `httpx==0.28.1` in `requirements-dev.txt`.
- CLI `run_tracking.py` behaviour and outputs unchanged.
- All message/event payloads carry `"schema_version": "1.0"`; events are exactly `event.to_dict()`.
- Defaults: `blur_heads=True`, `frame_stride` int 1–10 (default 1), optional `max_frames ≥ 1`, max upload 500 MB, host 127.0.0.1, port 8000.
- Style: match existing modules (frozen dataclasses, type hints, short docstrings, line length 110); `ruff check .` and `ruff format --check .` clean after every task.
- Never fabricate results; only the planner edits `docs/testing_report.md`.

## Review Focus

1. A file with a valid extension that OpenCV cannot open → run ends `failed` with a readable error; worker continues with the next job (test in Task 3).
2. A WebSocket client disconnecting mid-run → processing continues, no error logged per frame, subscriber removed (test in Task 4).
3. `DELETE` of a `queued` run → removed from the queue and never processed (test in Task 3).
4. Two uploads back-to-back → second stays `queued` until the first finishes, then completes (test in Task 3).
5. An invalid camera YAML in `configs/cameras/` → `/api/cameras` lists it with its error and an upload naming it gets 400, other cameras still work (test in Task 4).

### Task 3: Job manager

**Files:**
- Create: `api/jobs.py`
- Test: `tests/test_api_jobs.py` (move shared fake tracker / tiny-clip helpers into `tests/conftest.py` if needed)

**Interfaces:**
- Consumes: Task 1 `process_video`, `FrameUpdate`; Task 2 `ApiSettings`, `db.*`.
- Produces in `api/jobs.py`:
  - `TrackerFactory = Callable[[], Any]` (returns an object with the `PersonTracker` interface); `default_tracker_factory(settings: ApiSettings) -> TrackerFactory` (loads `PersonDetector` once, lazily on first call; each call returns a new `PersonTracker(detector, TrackerSettings(new_track_confidence=config.CONFIDENCE))`).
  - `class JobManager(settings: ApiSettings, tracker_factory: TrackerFactory)`: `start() -> None` (opens its own DB connection in the worker thread; calls `db.mark_interrupted` before starting), `stop(timeout: float = 30.0) -> None` (sets stop flag; current job ends `cancelled`), `submit(video_id: int) -> None`, `cancel(video_id: int) -> bool` (queued → removed + `cancelled`; processing → stop flag for that job; else False), `is_active(video_id) -> bool`, `queue_depth -> int`, `live_state(video_id) -> dict | None` (latest progress message body), `subscribe(video_id, loop: asyncio.AbstractEventLoop) -> tuple[asyncio.Queue, Callable[[], None]]` (queue `maxsize=256`; returns unsubscribe), `wait_idle(timeout: float) -> bool` (tests).
  - Messages (dicts with `schema_version` and `type`), built by module functions `progress_message(video_id, update: FrameUpdate) -> dict`, `event_message(video_id, event: dict) -> dict`, `status_message(video_id, record: dict) -> dict`; fields per spec.
- Behaviour: job runs `process_video(upload_path, tracker, RunOptions(output_dir=settings.outputs_dir/str(id), camera=load_camera_config(camera_dir/f"{camera_id}.yaml"), frame_stride, max_frames, blur_heads), on_frame=..., should_stop=...)`. In `on_frame`: buffer every event dict; when the video second changes (first frame of each second, same rule as `QueueTimeSeriesWriter`) append a timeseries row, flush buffered events + rows + `set_progress` in one transaction, and publish one `progress` message; publish `event` messages immediately. Final flush, `set_report`, status `completed` (or `cancelled` if this job's stop flag was set) and a `status` message. Any exception → `failed` with `str(error)`, `status` message, continue. Publishing: `loop.call_soon_threadsafe(_put, queue, msg)`; when a queue is full, drop `progress` only.

- [ ] **Step 1: Write failing tests** with a fake tracker factory and a tiny generated clip (cv2 `VideoWriter`, 60 frames at 10 fps) and a tmp camera YAML with a service line:
  - `test_job_completes_and_persists`: submit → `wait_idle` → status `completed`, `frames_processed == 60`, timeseries row count 6, report stored, events stored equal the run's `events.jsonl` lines.
  - `test_subscriber_receives_progress_events_and_final_status` (message `type` order: progress/event..., last is `status` with `completed`; every message has `schema_version`).
  - `test_unreadable_video_fails_and_worker_continues` (Review Focus 1): a `.mp4` with junk bytes, then a good clip → first `failed` with non-empty error, second `completed`.
  - `test_second_upload_waits_for_first` (RF 4): fake tracker slowed by an event; second is `queued` while first `processing`; both end `completed`.
  - `test_cancel_queued_removes_it` (RF 3) and `test_cancel_processing_marks_cancelled` (partial rows kept).
  - `test_restart_marks_interrupted`: leftover `processing` row → `failed` "interrupted by server restart" after `start()`.
